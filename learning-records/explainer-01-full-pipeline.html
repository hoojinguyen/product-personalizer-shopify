The Template Editor — Where It All Starts

The most complex page is the Template Editor (app.templates.tsx — 3,128 lines). A Template is a reusable blueprint containing:

  • A list of customization options (text, swatch, file upload, clipart, checkbox, dropdown)
  • Canvas positioning for each option (X, Y, width, height, rotation, font size) on an 800×800 coordinate grid
  • Layout mode (stacked, tabs, or modal)
  • Brand colors and cart behavior settings
  • Optional upcharge prices per option
  • Conditional visibility rules (show option B only when option A equals "Yes")
💡
Why templates matter
Without templates, a merchant with 500 products would configure each one individually. Templates let them configure once and bulk-link to hundreds of products. The sync engine (Section 2) propagates changes downstream.

2 Template Sync — The Bridge to Storefront

When a merchant saves a template or configures a product, how does that data reach the buyer's browser? This is the job of Template Sync.

🟢
Shopify concept: Metafields
A metafield is a key-value pair attached to a Shopify resource (product, order, shop). Think of it as a custom column on a database table. This app uses the metafield namespace app and key customization_config to store JSON configuration on each product. It's set to PUBLIC_READ access so the storefront widget can read it — this is critical.

The Sync Engine Architecture

The sync engine lives in app/utils/templateSync.ts (439 lines) and uses a hexagonal architecture (ports & adapters):

// Port — abstract interface (testable, swappable)
interface ShopifyAdminPort {
  fetchProducts(ids): Product[]
  publishMetafields(payloads): void  // ← the core operation
}

// Adapter — concrete implementation using Admin GraphQL
class ShopifyAdminGraphQLAdapter implements ShopifyAdminPort {
  publishMetafields(payloads) {
    // Calls Shopify's metafieldsSet mutation
    admin.graphql(`mutation metafieldsSet($metafields: [MetafieldsSetInput!]!)`, ...)
  }
}

// Facade — public API the routes call
class PersonalizationConfigSync {
  static syncTemplate(context, input, productIds)     // template → DB + products
  static unsyncTemplate(context, templateId)            // delete + unlink all
  static syncProductConfig(context, productId, config)  // single product
  static publishRawMetafields(context, payloads)        // bulk raw publish
}

When sync runs, this JSON structure is written to product.metafields.app.customization_config:

  "brandColor": "#008060",
  "heading": "Personalize Your Item",

    {

Template → Product Linking

1
Merchant saves template with product links
Route calls PersonalizationConfigSync.syncTemplate()
2

💡
The rendering seam
The VisualLayoutRenderer is the most architecturally interesting part of the app. The same class renders to HTML5 Canvas (client-side for live preview) and compiles to SVG (server-side for manufacturing print files). This means the buyer's preview is pixel-accurate to the manufacturing output.
📤 File Upload Flow — App Proxy
🟢
Shopify concept: App Proxy
An App Proxy is a URL route hosted by Shopify that forwards requests from the storefront domain (e.g. mystore.myshopify.com/apps/personalizer/upload) to your app's backend server. This avoids CORS issues — the buyer's browser talks to the store domain, Shopify forwards to your server.

When a buyer uploads an image:

  1. Client POSTs FormData to /apps/personalizer/upload
  2. App Proxy forwards to app.proxy.upload.tsx
  3. Server authenticates via authenticate.public.appProxy
  4. ShopifyFilePublisher.publish() runs the 3-step pipeline: stage → S3 upload → register → poll for CDN URL
  5. Returns {success, fileId, url} — the CDN URL is stored in fieldValues[optionId]

4 Cart & Checkout — Where Pricing Happens

This is the most critical flow for buyer impact. When the buyer clicks "Add to Cart", a carefully choreographed sequence runs:

Cart Submission Interception

1
Intercept the native cart form
On mount, the widget finds the theme's form[action*="/cart/add"] and attaches a submit event listener
📄 storefront-widget/index.tsx — L278-287
2
Snapshot the canvas preview
canvas.toDataURL("image/png", 0.7) → convert to File → upload to /apps/personalizer/upload → get permanent CDN URL
3
Inject hidden form inputs
Creates hidden <input> elements in the intercepted form:
// Hidden properties injected into the cart form:
properties[_upcharge_amount] = "5.00"    // underscore prefix = hidden from buyer
properties[_preview_url]    = "https://cdn.shopify.com/..."  // hidden
properties[Your Name]       = "Alice"   // visible to buyer in checkout
properties[Color]            = "#FF0000" // visible to buyer
🟢
Shopify concept: Line-item properties
Shopify's cart supports properties on each line item — arbitrary key-value pairs. By convention, keys starting with _ (underscore) are hidden from the buyer in checkout and order confirmation, but still accessible to the app and admin. This is how the app hides internal data (_upcharge_amount, _preview_url) while showing buyer choices (Your Name, Color).

Cart Transform Function — Pricing Magic

🟢
Shopify concept: Cart Transform (Shopify Function)
A Shopify Function runs inside Shopify's infrastructure (compiled to WASM), not on your server. Cart Transform is a specific extension point that lets you modify cart line items at checkout — adjusting prices, merging items, or changing images. It runs automatically on every cart operation.

The Cart Transform Function reads the hidden properties and adjusts the price:

// cart-transform-function/src/cart_transform_run.ts
for (const line of cart.lines) {
  const upcharge = parseFloat(line.upchargeAmount?.value || "0")
  const previewUrl = line.previewUrl?.value

  if (upcharge > 0 || previewUrl) {
    const basePrice = parseFloat(line.cost.amountPerQuantity.amount)
    const newPrice = (basePrice + upcharge).toFixed(2)

    operations.push({
      update: {
        cartLineId: line.id,
        price: { adjustment: { fixedPricePerUnit: { amount: newPrice } } },
        image: previewUrl ? { url: previewUrl } : undefined
      }
    })
  }
}

// Example: $50 product + $5 upcharge → buyer sees $55 in cart
// Cart thumbnail shows their personalized preview instead of stock photo

Checkout UI Extension — Showing Choices

At checkout, a separate extension renders personalization details under each cart line item:

  • Filters out hidden properties (keys starting with _) to show only buyer-visible choices
  • If _preview_url exists, renders a thumbnail of the customized product
  • Shows a styled card with "✨ Your Customization Choices" listing each option as a key-value pair

5 Order Fulfillment — Manufacturing Pipeline

After the buyer completes checkout, a webhook triggers a background compilation pipeline that produces print-ready files for manufacturing.

🟢
Shopify concept: Webhooks
A webhook is an HTTP callback Shopify sends to your app when a specific event occurs. When an order is created, Shopify POSTs to your webhooks.orders.create.tsx endpoint with the full order payload. Your app must respond quickly (within 5 seconds) — hence the async background worker pattern.

The Background Worker Pipeline

1
Shopify fires orders/create webhook
webhooks.orders.create.tsx receives payload, extracts orderId
2
Enqueue job → return 202 immediately
enqueueWebhookJob() creates a PENDING OrderProcessingLog in SQLite. Deduplicates — if log exists and FAILED, resets to PENDING.
3
Background worker picks up PENDING jobs
ensureWorkerRunning() → singleton guard → setImmediate → processQueue() polls for PENDING logs
4
compilePrintFiles() — the heavy lifting
  1. Fetch order + line items via Admin GraphQL
  2. Filter personalized items (has custom attributes)
  3. For each item: fetch product metafield → resolve config
  4. Render SVG via VisualLayoutRenderer.compileToSvg()
  5. Publish SVG to Shopify Files → get CDN URL
  6. Write manufacturing_files metafield on the order
  7. Update log → COMPLETED

Fulfillment Package Download

When a merchant clicks "Download" in the Orders page, app.proxy.download.tsx calls packageFulfillment() which streams a ZIP containing:

The SVG compilation seam (again)
Remember the VisualLayoutRenderer from Section 3? Server-side, its compileToSvg() method fetches font binaries from the Asset DB, base64-encodes them as @font-face data URIs, inlines images as base64, and adds production cut lines with order/item metadata. Same coordinate math, different output format.

🗃️ Database Models (SQLite + Prisma)

The app uses SQLite locally with 6 standalone models (no foreign key relations — all cross-model lookups done via shop key):

ModelPurposeKey Fields
SessionShopify OAuth tokensshop, accessToken

💡
Why no Prisma relations?
Each model is scoped by shop (the Shopify store domain). Cross-model relationships are managed in application code rather than at the database level. This keeps the schema simple but means you can't use Prisma's include for eager loading — every join is manual.

🧠 Question 1

How does the storefront widget get the customization config for a product?

✅ Correct! The Liquid block reads product.metafields.app.customization_config.value and passes it as data-config on the mount div. The React app then parses this JSON on DOMContentLoaded. No API call needed — the data is already in the page.
❌ Not quite. The config is already on the product as a metafield. The Liquid block reads it server-side and embeds it as a data-config attribute — no client-side API call needed.

🧠 Question 2

Why does the Cart Transform Function exist? Why not just add the upcharge on the client side?

✅ Correct! If you only changed the displayed price in JavaScript, a savvy buyer could manipulate the DOM or use browser devtools to avoid the upcharge. Cart Transform runs as a WASM function inside Shopify's servers — it's tamper-proof. Shopify enforces the adjusted price at checkout.
❌ The key insight is security. Client-side price changes are trivially bypassable. Cart Transform runs inside Shopify's infrastructure (as WASM), making it tamper-proof. The function adjusts the actual checkout price, not just the display.

🧠 Question 3

What bridges the storefront widget data to the Cart Transform Function?

✅ Correct! The widget injects hidden <input> elements with names like properties[_upcharge_amount] into the native cart form. These become line-item properties that the Cart Transform Function reads via its GraphQL input query. The underscore prefix hides them from the buyer.
❌ The bridge is line-item properties. The widget injects hidden form inputs (properties[_upcharge_amount]) that Shopify attaches to the cart line. The Cart Transform Function reads these via its GraphQL input query.

🧠 Question 4

Why does the webhook handler return 202 immediately instead of compiling print files synchronously?

✅ Correct! Shopify expects webhook responses within 5 seconds — if you exceed this, Shopify will retry the webhook (and eventually disable it). Compiling SVGs, publishing to Shopify Files, and polling for CDN URLs can take 10-30+ seconds. So the handler enqueues a PENDING job and returns 202, letting the background worker process it asynchronously.
❌ The constraint is Shopify's webhook timeout (~5 seconds). SVG compilation + file publishing is slow (10-30+ seconds), so the handler must return immediately and process the job asynchronously via a background worker.

🧠 Question 5

What makes VisualLayoutRenderer architecturally special?

✅ Correct! This is a rendering seam — a single abstraction with two implementations sharing the same coordinate math. drawToCanvas() runs client-side for real-time preview. compileToSvg() runs server-side for manufacturing. Because they share the same LayoutNode resolution and positioning logic, the buyer's preview is faithful to the final manufacturing output.
❌ The key is the shared seam pattern. drawToCanvas() (client) and compileToSvg() (server) share the same coordinate math and layout node resolution. This means the buyer's live preview accurately represents the final manufactured output.
